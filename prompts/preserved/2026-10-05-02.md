## The behaviour

In a **debug build only**, whenever a track recording runs, the logger records, to a file on the phone, everything below with its own timestamps. It stops when the recording stops. Nothing changes for the walker. In a release build the logger does not exist: no code, no permission, no file. That follows the pattern `diagnostics/DebugDiagnostics.kt` already uses, with a no-op twin in `app/src/release`.

What it records, each item if the phone offers it, and an explicit "unsupported" line if not:

1. **Every location fix from GPS, network and passive,** with provider, accuracy, vertical accuracy, speed and its accuracy, bearing and its accuracy, altitude, `getTime()` and `getElapsedRealtimeNanos()`. Network fixes included (-519: collected, never relied on).
2. **Satellite status** (`GnssStatus`), each callback: every satellite's constellation, id, signal strength (C/N0), elevation, azimuth, used-in-fix, and carrier frequency, which shows whether the S22 tracks L5.
3. **Raw GNSS measurements and their capabilities** (`GnssMeasurementsEvent`, `GnssCapabilities`), including the accumulated delta range state, which shows whether carrier phase is offered. If the phone offers none, say so once.
4. **Steps:** step detector events and the step counter.
5. **Motion and heading:** rotation vector, game rotation vector, gyroscope, accelerometer and magnetometer, at a rate you propose, with the sensor's reported accuracy changes.
6. **Barometer** (pressure).
7. **Battery level and charging state** every minute. Battery is a recorded gap (-519, -520), and this costs almost nothing.
8. **A header:** device model and build (`getprop`), app version, the start time, and every sensor's name, vendor and reported range. A device's reported range describes what is possible, not what is safe (CLAUDE.md).
