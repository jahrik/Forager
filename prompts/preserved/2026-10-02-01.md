## The planner's diagnosis: confirm each, or show where it is wrong

1. **The off-track decision and all its state live in the screen's ViewModel.** The decision and the one `deliver` call: `ui/track/TrackRecordingViewModel.kt:824-833`. The rolling window `:177`, the cooldown `:182`, the returning flag in the UI state (`startReturn` `:425`, `stopReturn` `:437`). All of it is cleared with the Activity (`onCleared` `:855`).
2. **The service knows a track id and a mode and nothing else.** `service/TrackRecordingService.kt`: it collects its own fixes, samples and batches them. It has no start point, no returning flag, and no reference to `AlertDelivery`.
3. **After a swipe-away the process lives, the service records, and a reopened app does not know.** The ViewModel's `activeTrack` is in-memory (its header, about `:72-78`), and `resyncRecordingState` returns at once when it is null (`:403`). So the planner reads: the reopened screen shows no recording while the service is still recording. **Read, not run.**
4. **A second recording could then be started over the first.** The planner reads: pressing record creates a new Track row and sends `ACTION_START`, which the service ignores because `recordingJob` is not null (`service/TrackRecordingService.kt:82`), so the screen would show a new track while the points go to the old one. **Read, not run. This is the premise most likely to be wrong; settle it first.**
5. **The two sundown alerts have no caller, on purpose.** `domain/DecideSundownAlertUseCase.kt:46` is called from nowhere in `app/src/main`; the comment at `TrackRecordingViewModel.kt:486-488` says alert delivery must not hang off the screen's loop.
6. **If the process itself is killed, nothing resumes.** `START_STICKY` redelivers a null intent, and `onStartCommand` starts nothing without `ACTION_START`. **Read, not run. Out of scope to fix; report what you find.**

If any of these is wrong, that is a finding: say so at the top of the report.
